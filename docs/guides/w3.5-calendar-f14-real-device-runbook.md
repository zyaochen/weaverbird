# W3.5 Calendar Hook / F14 Periodic Inspect — Real-device Runbook

> **Audience**: owner / operator  
> **Scope**: blocked-pending real-device verification for Calendar Hook and F14 periodic inspection  
> **Status**: manual-only runbook  
> **Rule**: this document records **human-executed** real-device steps only; agent must not execute real calendar or IM outbound actions without explicit approval

---

## 0. Why this runbook exists

W3.5 has already closed the **local chain + L1 mock** loop for:

- Calendar Hook
  - long-run block open / close
  - fail-safe timeout + local sidecar
  - ingress source wiring
- F14 periodic inspection
  - periodic task registry
  - occurrence materialization
  - skip / queue_one reentry behavior
  - scheduler → ingress → existing run execution path

What is still **blocked-pending** is any **real external action**:

1. real calendar create / close
2. real periodic trigger causing a true run in a real bot context
3. real IM echo / notification back into the home group
4. real cross-external idempotency validation

This runbook is the manual closure checklist for those items.

---

## 1. Hard red lines

Stop immediately and ask for a fresh authorization if any step would:

- create / update / delete a **real** calendar event
- send a **real** IM message/card into a real home group
- trigger a **real** periodic run against a production-like target
- require changing production bot credentials, production group membership, or production scheduler configuration

Also stop if any evidence would record:

- real token / app secret / access token
- real `open_id` / `chat_id` / `thread_id`
- unredacted screenshots from a real group

## 3. Config checklist

## 3.1 Calendar Hook config

Confirm `config/calendar-hook.json` is present in the active `WB_DATA_DIR` and uses the intended test calendar:

- `enabled = true`
- `transport = cli` or the real transport mode you are validating
- `calendar_id` points to the **test calendar**
- `rpc_timeout_ms` is set
- `overdue_after_ms` is set
- `sweep_interval_ms` is set

## 3.2 Periodic tasks config

Confirm `config/periodic-tasks.json` is present and only includes **test** tasks:

- `enabled = true`
- every `task_id` is test-only
- every `target.home_group_id` is a test group
- every `target.cwd` points to a safe repo/worktree
- every `run_template.text` is non-destructive
- default `reentry.policy = skip` unless you are explicitly validating `queue_one`

## 4. Calendar Hook real-device verification

## CH-1 · real block open on running

**Goal**: verify a real long-running run creates a real calendar block.

### Steps
1. Ensure the bot is online in the test group.
2. Trigger a clearly long-running request in the test group.
3. Wait until the run is visibly in `running` state.
4. Check the test calendar manually.

### Expected
- exactly one block is created
- block title contains the expected run title
- block time window matches configured `overdue_after_ms` / runtime expectation
- the run's local sidecar `runs/<bot>/<run>/calendar-hook.json` contains:
  - `calendar_block_id`
  - `desired_state = open`
  - `calendar_hook_failed = false`

### Failure notes
If no block appears:
- check bot logs
- check `calendar-hook.json`
- confirm `transport` and `calendar_id` are pointed at the test calendar
- do **not** retry against a production calendar

---

## CH-2 · real block close on terminal

**Goal**: verify the real block is closed when the run reaches terminal state.

### Steps
1. Reuse the run from CH-1 or trigger a new safe run.
2. Let it finish naturally, or stop it through the normal control path.
3. Check the same calendar block again.

### Expected
- the block is updated/closed exactly once
- no duplicate second block is created
- `calendar-hook.json` shows:
  - `desired_state = closed`
  - `close_revision_applied` present
- run terminal accounting still completes

### Failure notes
If the block remains open:
- confirm the run reached terminal state
- inspect `calendar_hook_failed`
- inspect run-registry projection fields
- do not manually delete the event until evidence is collected

---

## CH-3 · fail-safe on real calendar timeout / failure

**Goal**: verify calendar failure does not block run accounting.

### Steps
1. Intentionally point the calendar transport at a failing test target, or temporarily force timeout conditions in a test-safe way.
2. Trigger a run.
3. Let the run complete.

### Expected
- run still reaches terminal state
- run terminal accounting still lands
- `calendar_hook_failed = true`
- local sidecar records `last_error`
- subsequent runs still execute normally

### Failure notes
If the run itself is blocked waiting on calendar I/O, stop and record it as a regression: this violates the fail-safe requirement.

---

## CH-4 · cross-external idempotency

**Goal**: verify that real external calendar operations are idempotent enough for production use.

### Steps
1. Re-trigger the same real run identity / replay path if your transport supports it.
2. Repeat open/close from the same `run_id` and revision boundary.
3. Inspect the calendar and sidecar state.

### Expected
- no duplicate real block is created for the same `run_id`
- replaying the same terminal close does not create a second mutation
- sidecar state remains stable

### Record explicitly
If the external system cannot prove strict idempotency, keep the feature tagged as **blocked-pending** and do **not** promote to `-close` semantics.

## 5. F14 periodic inspection real-device verification

## F14-1 · periodic task registration is loaded

**Goal**: verify the runtime reads the real task registry.

### Steps
1. Place a single safe test task in `config/periodic-tasks.json`.
2. Reload or restart the relevant runtime.
3. Confirm the runtime accepts the config without parse errors.

### Expected
- no config parse error
- no secret printed to logs
- periodic task state files can be created under `periodic-tasks/`

---

## F14-2 · one due window triggers one real run

**Goal**: verify one periodic window produces exactly one real run.

### Steps
1. Configure one test task with a short interval.
2. Wait until one due window passes.
3. Observe the test group and local state.

### Expected
- exactly one occurrence is materialized
- exactly one real run is spawned
- `periodic-tasks/state.json` shows active occurrence info
- `periodic-tasks/occurrence-ledger.ndjson` contains one `spawned` record
- `runs/<bot>/<run>/periodic-task.json` is present

---

## F14-3 · same window replay is idempotent

**Goal**: verify the same periodic window cannot spawn twice.

### Steps
1. Force a reload or second tick during the same due window.
2. Re-check ledger and active runs.

### Expected
- no second run is spawned
- no duplicate occurrence record for the same `occurrence_id`
- ledger remains append-only and idempotent

---

## F14-4 · skip reentry (default)

**Goal**: verify the default policy skips the next window while the previous run is still active.

### Steps
1. Configure a long-running periodic task with `reentry.policy = skip`.
2. Let one occurrence start.
3. Wait for the next due window while the first run is still active.

### Expected
- no second run is spawned
- ledger contains `skipped_busy`
- state updates `last_decision = skipped_busy`
- scheduler continues running normally for later windows

---

## F14-5 · queue_one reentry (optional explicit validation)

**Goal**: verify only one pending occurrence is retained.

### Steps
1. Switch one test task to `reentry.policy = queue_one`.
2. Start one long-running occurrence.
3. Let two further windows pass while the run is still active.

### Expected
- no unbounded queue growth
- only one queued occurrence is retained in state
- once the active run finishes, the latest queued occurrence is promoted exactly once

---

## F14-6 · single failure does not block later windows

**Goal**: verify scheduler fail-safe behavior.

### Steps
1. Cause one occurrence to fail at dispatch or run time.
2. Wait for the next due window.

### Expected
- ledger contains `dispatch_failed` or equivalent failure record for the failed occurrence
- the next occurrence still fires normally
- scheduler remains healthy
- no manual reset is required just to continue later cycles

## 6. Real IM echo / notification verification

## IM-1 · start echo to home group

**Goal**: verify periodic run start is visible in the home group.

### Steps
1. Use a test task whose target points at a test home group.
2. Let one occurrence fire.
3. Inspect the test group.

### Expected
- a start-facing card/message appears in the home group
- it is tied to the correct run/occurrence context
- no duplicate start echo for the same occurrence

## IM-2 · terminal echo / finalize

**Goal**: verify terminal state is visible in the home group or thread through the existing path.

### Steps
1. Let the periodic run finish.
2. Observe the group/thread.

### Expected
- terminal summary/alert uses the existing rendering path
- no second custom renderer is involved
- the message content does not leak secrets or private identifiers

## IM-3 · failure path

**Goal**: verify notification failure does not block scheduling.

### Steps
1. Intentionally fail the notifier in a test-safe environment.
2. Trigger one occurrence.
3. Let a later occurrence fire.

### Expected
- scheduler continues
- a local fallback/ledger record exists
- later occurrences are still processed
